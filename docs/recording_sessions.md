# Calibrated multichannel recording sessions (Phase 6D)

Phase 6D groups managed WAV uploads with explicit calibration metadata and applies the existing Phase 5E.1 multichannel TOA extraction. It does not implement reconstruction, room geometry estimation, or echo-to-wall assignment.

## Data and provenance

The versioned session API stores a project-scoped session, calibration JSON, analysis settings, WAV references, recording start times, channel maps, per-event selection, and extraction jobs/results. WAV bytes remain in the existing managed recording store. The session endpoints attach previously imported files; upload remains `POST /api/recordings`.

Provenance is one of `synthetic`, `imported_real_multichannel`, or `laptop_single_device`. Laptop single-device mode is retained as metadata but is rejected for calibrated array extraction. A multichannel extraction requires the metadata to assert synchronized clocks and describe the evidence/acquisition method. BatSight does not independently verify synchronization.

## Metadata contract example

The following is illustrative data only. Replace every coordinate, time, sound speed, sample rate, waveform description, and synchronization statement with values supported by the acquisition record. `null` and empty collections are used by the UI draft template so missing measurements remain visible; validation prevents extraction until required fields are supplied.

The same complete example is available as [calibrated_session_metadata.example.json](examples/calibrated_session_metadata.example.json).

```json
{
  "schema_version": "1.0",
  "coordinate_frame": "corner_origin_x_length_y_width_z_height",
  "position_unit": "m",
  "time_unit": "s",
  "time_reference": "acquisition clock epoch documented by operator",
  "sample_rate_hz": 48000,
  "speed_of_sound_m_s": 343.0,
  "synchronization": {
    "status": "synchronized",
    "evidence_description": "Document the shared clock or synchronization procedure"
  },
  "microphones": [
    {"microphone_id": "mic-01", "position_m": [0.5, 0.5, 1.2]},
    {"microphone_id": "mic-02", "position_m": [1.0, 0.5, 1.2]}
  ],
  "events": [
    {
      "event_id": "event-01",
      "source_id": "source-01",
      "position_m": [2.0, 1.5, 1.4],
      "emission_time_s": 10.0,
      "reference_signal": {
        "waveform": "linear_sweep",
        "duration_s": 0.02,
        "start_frequency_hz": 700,
        "end_frequency_hz": 12000,
        "amplitude": 0.8
      }
    }
  ]
}
```

Coordinates are metres in the declared corner-origin Cartesian convention; times are seconds in the explicitly named shared reference; sample rate is Hz; sound speed is m/s. Generic sine and linear-sweep references are generated by the existing engineering waveform module. They do not claim to reproduce unresolved Equation 10 of the 2016 paper.

Analysis configuration accepts the existing Phase 5E.1 settings (`direct_tolerance_s`, echo excess-delay bounds, separation, sliding-window `window_length_samples`, `thr1`, `thr2`, prominence, polarity, and optional `timing_uncertainty_s`). These are configurable analysis values, not automatically calibrated physical quantities.

For each recording, `recording_start_time_s` is in the same shared time reference as event emission times. Each file must map every zero-based audio channel to a calibrated microphone ID exactly once. The same microphone may be mapped in separate files. BatSight does not infer a map, resample, or synchronize separate files.

## API workflow

1. Import WAV bytes using `POST /api/recordings` with a project ID.
2. Create a session using `POST /api/v1/recording-sessions` with provenance, calibration, and analysis configuration.
3. Attach each imported recording using `POST /api/v1/recording-sessions/{session_id}/recordings`, including recording start time, complete channel map, and optional event IDs.
4. Inspect and correct metadata using `PUT /api/v1/recording-sessions/{session_id}/metadata`.
5. Call `POST /api/v1/recording-sessions/{session_id}/validate`. Validation returns actionable errors and warnings.
6. When valid, queue `POST /api/v1/recording-sessions/{session_id}/extractions`; poll the returned job with `GET /api/v1/recording-sessions/{session_id}/extractions/{extraction_id}` or fetch the latest with `GET /api/v1/recording-sessions/{session_id}/results`.

Create body:

```json
{
  "project_id": 1,
  "name": "Array capture 2026-11-11",
  "provenance": "imported_real_multichannel",
  "calibration": {"schema_version": "1.0", "coordinate_frame": null, "position_unit": null, "time_unit": null, "time_reference": null, "sample_rate_hz": null, "speed_of_sound_m_s": null, "synchronization": {"status": "unknown", "evidence_description": null}, "microphones": [], "events": []},
  "analysis_configuration": {}
}
```

The example intentionally represents an incomplete draft; it cannot pass extraction validation.

## Result interpretation

Results include original recording metadata, a bounded min/max waveform envelope for display, pair-level expected direct times, observed/missing direct-path candidate state, unclassified echo candidates, rejected peaks and rejection reasons, matched-filter strengths/noise diagnostics, and observation-adapter output with provenance. No real-data echo is assigned a wall or reflection order. Results explicitly set `estimated_room_geometry_available` to `false`.

The background job runner is in-process and local. A process interruption is not handled by a durable queue. The result contains an assertion about synchronization metadata, not a validation of it. Direct candidate selection uses declared calibrated positions and times, as specified by the existing Phase 5E.1 analyzer; inaccurate metadata can therefore affect candidate categorization.
