# Phase 6C — Interactive 3D Workspace

## Scope and provenance

The workspace is a geometry editor and visualizer, not a room-reconstruction algorithm. Editable scenes are user-authored. Path previews are generated by the existing ideal shoebox image-source simulator and carry `visualization_only_simulated_prediction_from_editable_scene` provenance. Stored experiment results are loaded from the API and are displayed as synthetic forward simulation with known synthetic ground-truth geometry. The canonical stored envelope uses `data_classification: "synthetic_forward_simulation"` and `geometry_status: "known synthetic ground truth"`, with `is_room_reconstruction: false` and `real_world_validation: false`. The frontend adapter accepts only this contract. No current API result contains estimated geometry, so the interface always reports estimated geometry as unavailable. It does not infer, substitute, or compare an estimate against ground truth. The frontend integration fixture is generated from `SyntheticExperimentService._run` and wrapped with the service's persisted-result contract.

Laptop microphone recordings remain a separate single-device signal-analysis workflow. They do not provide a synchronized multichannel array or a complete uncalibrated 3D reconstruction.

## Component architecture

- `frontend/src/workspace3d/Workspace3D.tsx` owns scene selection, local persistence, experiment loading, API preview requests, inspector state, and viewport composition.
- `sceneModel.ts` provides the JSON scene schema, bounds validation, safe restore behavior, and pure geometry helpers.
- `experimentGeometry.ts` is a provenance-gated adapter from the actual synthetic experiment result envelope to display records. Unsupported or incomplete result data throws a visible error rather than fabricating geometry.
- The R3F viewport uses Three.js primitives, Drei `OrbitControls`, `TransformControls`, `Html` labels, and axis gizmo. It has no renderer-object persistence.
- `POST /api/simulation/paths` calls the existing `ShoeboxRoom` and `predict_acoustic_paths`; it is a narrow forward-only adapter, not a second path implementation.

## Coordinates and room geometry

The world frame is right-handed Cartesian XYZ with metres: the room corner is `(0,0,0)`, X is length, Y is width, and Z is height. Room dimensions are `[Lx,Ly,Lz]`. Six axis-aligned boundary planes are at `x=0/Lx`, `y=0/Ly`, and `z=0/Lz`. This matches the existing simulator convention. Editable room dimensions are bounded to 0.5–100 m as a UI validation choice. The scene model requires equipment coordinates to be strictly inside the room; dragged and numeric positions are clamped to a small interior margin.

The room is rendered with low-opacity faces and edge lines. Speakers and microphones use different colors and simple low-polygon markers. Orientation is stored as a yaw angle about Z and shown on the marker. This is a visualization convention; it does not model directivity.

## Paths and image sources

For an editable scene, a debounced API request predicts order 0, 1, or 2 paths from the first visible speaker to visible microphones. Direct paths are drawn source-to-receiver. First-order paths are drawn source-to-finite-wall bounce-to-receiver only when the backend reports a finite valid bounce point. The backend computes that point by intersecting the image-source-to-receiver line with the identified axis-aligned plane and checking the other two coordinates against the finite wall extent.

Higher-order output is shown only when supplied by the existing simulator; it is rendered as a virtual image-source ray and marked as a higher-order virtual path. The simulator does not validate order-two sequences as finite bounce trajectories, and the UI does not invent such a trajectory. The image-source toggle shows virtual image positions/rays; an image is not a physical source or estimated source position.

Path length and TOF are retained from the simulator and available in stored experiment details. Every path label says simulated or visualization-only; none is called measured. The display order selector filters available supported simulator orders.

## Experiment integration

The selector lists actual experiment records from `/api/experiments` and fetches `/api/experiments/{id}/results`. The adapter requires the existing synthetic-forward classification, known synthetic geometry marker, room dimensions, source, microphones, and path records. It shows experiment ID/type/status and the known-ground-truth provenance. Missing geometry causes a visible explanatory error. The experiment view is read-only. “Save as editable scene” explicitly copies a snapshot into the independent local editor; it does not mutate the experiment record.

There is no ground-truth/estimate comparison because no estimate field is currently available. No accuracy metric is calculated in this workspace.

## Persistence

Local storage uses a versioned JSON document containing schema version, coordinate convention, metre units, room dimensions, speed of sound, and equipment IDs/names/types/positions/yaw/visibility. Scene records are scoped by active project ID (or a default unscoped key). Display toggles are persisted separately. Camera transforms, Three.js objects, transient hover/selection, API preview responses, and experiment records are not serialized as scene state. Experiment result data remains in the backend and is never overwritten by local scene edits.

## Limitations and future work

- The path preview represents an ideal shoebox image-source calculation, not measured audio or a full wave-acoustic simulation.
- Frequency-dependent absorption, diffraction, scattering, microphone directivity, transducer response, and environmental variation are not modeled by this viewer.
- Second-order wall sequences are virtual image-source operators and are not checked as finite physical bounce paths.
- Current experiment results contain known synthetic geometry; estimated geometry is unavailable.
- Manual object placement is not measurement/calibration. One laptop microphone does not reproduce the paper's synchronized multichannel observation requirements.
- Multiple speakers are editable, while the current path-preview API contract accepts one source at a time; the preview uses the first speaker. This is explicit in the interface architecture and should be generalized only with an API contract change.
- Drag clamping enforces interior coordinates, but this is a UI editing constraint, not a claim about arbitrary physical setups.
- Browser rendering and pointer controls require WebGL. On narrow screens the panels stack; desktop remains the intended editing layout.

## Use

Start the API as documented in the root README, then run `npm install` and `npm run dev` from `frontend/`. Open **3D Workspace** in the sidebar or navigate to `/workspace/3d`. Select the room to edit dimensions and sound speed, add equipment with `S` or `M`, select a marker and edit its coordinates or yaw, or drag its transform gizmo. Toggle path order, walls, grid, axes, labels and virtual images in the toolbar. Select a completed supported synthetic experiment to inspect its actual saved result. Editable scenes persist locally per project.
